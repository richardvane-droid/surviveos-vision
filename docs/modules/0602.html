🎬 沉浸式想象

凌晨四点二十，你在木屋里睡得正香，草地中段东墙下那根一米高的木杆顶上，翻斗雨量计刚刚归零，土壤探针回报根区含水率 21%，比阈值低了 4 个点，雨水罐水位 62%。杆子里那块 XIAO ESP32C6 不到一秒算完：“浇，中段草原 8 分钟，北段疏林 12 分钟。”电磁阀“咔”一声，草根下的滴管开始渗水，整片草地没有一滴水飞起来。早上七点你端着咖啡看手机，HomeAssistant 卡片上一根曲线平稳抬高，底下一行小字：今晨已浇灌，雨水 96L，自来水 0L。

✅ 设想方案清单

  1. 三传感器：Grove 电容式土壤湿度探针埋 15cm 深各区一根，翻斗雨量计装杆顶，雨水罐内超声波水位计
  2. XIAO ESP32C6 跑 ESPHome，本地判断不依赖云：含水率低于阈值 + 未来 6 小时无雨 + 罐里有水才开阀
  3. 三路 12V 电磁阀装在东墙雨水罐旁，分别控北段疏林/中段草原/南段野花，干管沿长边分段铺，各区阈值不同，芒草 18%、朴树 25%、野花 22%
  4. 浇灌时段锁死在凌晨四到六点，蒸发最少，白天绝不浇，除非手动按木杆上那颗大红按钮
  5. 传感器杆用 8cm 方料桧木，顶上做小斜屋顶防雨，控制盒藏在杆内，只露一颗指示灯
  6. HomeAssistant 做“草地体检”卡片：三区含水率曲线 + 本周用水量 + 雨水占比，接入 0802 大屏
  7. 每区留一个手动快接口，冬天排空管路防冻

Seeed-Studio/xiao-esphome-projects ★ 37 无中文

Seeed 官方的 XIAO 加 ESPHome 工程合集：电能计量、土壤湿度、mmWave、2 路 6 路继电器，都是现成 YAML

→ 0805 把 XIAO 加 Grove 定为全屋器件基准，这仓库的土壤湿度与继电器两个工程正好凑成杆内那块板；星数低，但它是这套器件唯一的官方现成工程。

xiao-esphome-projects 是 Seeed 官方放出的 XIAO 加 ESPHome 工程合集，一个子目录一份可以直接烧录的 YAML，配接线图和 Seeed Wiki 上的对应页。仓库只有 37 星，却不是社区玩票，而是 0805 定标的这套器件唯一的一手示例，拿到板子当天就能把一个传感节点挂进 HomeAssistant。

工作方式就是 ESPHome 那一套：YAML 写清这块 XIAO 上接了什么外设、多久读一次、什么时候深睡，编译烧进去，上电后用原生 API 直连 HomeAssistant，不经云也不必架 MQTT。现成工程覆盖电能计量、土壤湿度、IoT 按钮、24GHz mmWave 和 2 路 6 路继电器。

硬件面向 XIAO ESP32C3 / C6 / S3，配 Grove 扩展板一插就是标准接口，不用自己打样。文档是英文的，但每篇都指回 Seeed Wiki 的中文页，配置语法又是 ESPHome 通用的；更新跟着新板子走，2025 年之后仍在加工程。

放进 0602 就是桧木杆里那块板：6 路继电器工程直接对应三路 12V 电磁阀，土壤湿度工程复制三份对应北中南三段探针，翻斗雨量计按脉冲计数挂上去，三条件判断在 XIAO ESP32C6 本地跑完再开阀，断网也不误凌晨那一轮。坑是杆内空间小，继电器和天线要隔开，不然一开阀 Wi-Fi 就掉。

esphome/esphome ★ 11.7k 无中文（社区教程多）

用 YAML 配置 ESP32 固件的系统，土壤湿度、翻斗雨量、超声波水位、电磁阀都是现成组件，本地跑逻辑，原生接 HomeAssistant

→ 桧木杆里那块 ESP32 就靠它：三传感器读数、三条件本地判断、三路阀门用 sprinkler 组件轮浇，断网照常，大红按钮也是它一行配置

ESPHome 是 Nabu Casa 维护的 ESP32 固件生成系统，和 HomeAssistant 同一个团队，GitHub 上 11.7k 星。想让 ESP32 读传感器、开关继电器、跑一点判断逻辑，以前得写 Arduino 代码，而它只要一份 YAML 写清接了什么、往哪报，编译、烧录、OTA 全自动。

它的工作方式是 YAML 到 C++ 的编译器：你声明传感器型号、引脚、采样周期，它生成固件；固件在设备本地运行，原生 API 推给 HomeAssistant，断网照常。和灌溉相关的组件很全：adc 读电容湿度探针，pulse_counter 数翻斗雨量计的脉冲，ultrasonic 读罐内水位，switch 控继电器，专门的 sprinkler 组件内置多路阀门排队轮浇和主阀联动。没有官方中文，但中文社区极大。

在 0602 里它就是桧木杆里的大脑：一块 ESP32 接三根湿度探针、雨量计和水位计，三路电磁阀经继电器接 sprinkler 组件；凌晨四点检查每区含水率低于阈值、罐里有水、HomeAssistant 传来的六小时降雨预测为零，三条都满足才把该区加入本轮；木杆上的大红按钮接一个 GPIO，按下就手动跑一轮。要注意电容探针要在干土和饱和土各标定一次，ADC 用 11dB 衰减并取五分钟中位数；三路阀门共用 12V 电源时加续流二极管。

altmenorg/HAsmartirrigation ★ 550 界面有中文

HomeAssistant 智能灌溉组件，按蒸散量和降雨算每个分区的水桶余额，给出该浇多少秒，界面自带 19 种语言含简体中文

→ 三区各建一个分区，它按天气算出疏林、草原、野花各要浇几分钟，替代拍脑袋的固定时长，再把秒数交给桧木杆里的 ESP32 执行

Smart Irrigation 是荷兰开发者 altmenorg 维护的 HomeAssistant 自定义集成，GitHub 上 550 星。固定时长的浇水要么浪费要么不够，科学的做法是算蒸散量，缺多少补多少，而这套农业公式普通人算不动。

它的工作方式是水桶模型：每个分区有一个虚拟水桶，每天用 FAO-56 的 Penman-Monteith 公式，按温度、湿度、风速、日照算出蒸散量从桶里扣掉，降雨往桶里加，桶低于零就表示缺水，缺的毫米数除以你填的滴灌流量就是该浇多少秒。天气数据可以来自 OpenWeatherMap，也可以完全用你自己的传感器；每个分区可设土壤类型、植物系数、面积和流量。它只负责算，秒数放在实体里由你的自动化去执行。界面有 19 种语言，含简体中文，更新频繁。

在 0602 里它是算账的那一层：疏林带、草原带、野花带各建一个分区，面积填 35、40、25 平米，植物系数按乔木、观赏草、宿根花分别取；雨量计的日累计和本地温湿度接进去替代网络天气。每天凌晨三点它算完，HomeAssistant 把三个秒数通过原生 API 写进桧木杆 ESP32 的 sprinkler 时长，四点由 ESP32 结合含水率和水位做最后判断。要注意地埋滴灌的湿润范围小，蒸散公式假设整面浇透，前两周对照探针实测把植物系数调低，别按默认值浇。

OpenSprinkler/OpenSprinkler-Firmware ★ 543 无中文

OpenSprinkler 开源灌溉控制器的统一固件，跑在 ESP8266 或树莓派上，多站点排程、天气调节、雨和土壤传感器输入、MQTT

→ 不想自己写 YAML 的备选路线：三路阀接一块 OpenSprinkler 板，站点排程和传感器跳过是十年打磨过的成熟逻辑，手机 App 直接管

OpenSprinkler 是美国 Rayshobby 公司从 2011 年做起的开源灌溉控制器，硬件和固件都开源，这个仓库是它的统一固件，GitHub 上 543 星，2025 年 11 月还在发新版。它把多路电磁阀灌溉做成一个能联网、按天气自动调、有手机 App 的控制器，是 DIY 灌溉领域里资格最老的项目。

同一套 C++ 代码可以编译给 ESP8266 版的 OpenSprinkler 3.x、树莓派版的 OSPi 和任何 Linux 机器。核心概念是站点和程序：每个站点对应一路电磁阀，程序定义哪些站点在什么时间浇多久；天气调节模块按气象数据算一个百分比缩放浇水时长；传感器输入支持雨传感器、土壤湿度开关和流量计，触发就跳过或暂停；网页和 App 通用，有 MQTT 和 HTTP API。硬件可买成品也可照原理图自制。没有中文资料。

在 0602 里它是不写代码的备选路线：三路 12V 电磁阀接三个站点，程序设成凌晨四点一轮，疏林 12 分钟、草原 8 分钟、野花 6 分钟；雨量计接它的雨传感器输入，下雨自动跳过，土壤探针经 ESP32 比较阈值后给它一个干接点当土壤传感器，太湿也跳过；雨水罐水位低时用 API 把它整体禁用。要注意它的传感器输入只认开关量，三区不同阈值得在 ESP32 那边分别比较；天气单位默认英制，改成公制。

node-red/node-red ★ 23.6k 界面有中文 延伸

IBM 起家、OpenJS 基金会维护的低代码流程编排工具：在浏览器里拖节点连线，把 MQTT、HTTP、定时器和逻辑串成流

→ 土壤、雨量、水位三个传感器开会这件事，用 Node-RED 画成一张流程图比写 YAML 自动化直观得多，改阈值也是拖一下的事

Node-RED 是 IBM 新兴技术团队 2013 年做出来的可视化编程工具，2016 年捐给 JS 基金会（现 OpenJS 基金会），Node.js 写的，23.6k 星，是物联网圈里事实上的流程编排标准。它解决的问题是：设备和 API 之间的胶水逻辑用代码写太琐碎，画成图反而清楚。

它的工作方式是流：浏览器里的编辑器把节点拖到画布上，连线表示消息的流向，每条消息是一个 JavaScript 对象；节点分输入（MQTT 订阅、HTTP 请求、定时器）、处理（函数、开关、延迟、合并）、输出（MQTT 发布、邮件、文件）。点部署，流就跑在 Node.js 运行时里。仪表盘节点能顺手生成一个网页面板。

生态上它的节点仓库有几千个社区节点，HomeAssistant 有官方插件和专门的节点集，HA 的实体状态和服务调用都能当节点用。编辑器界面有简体中文，中文教程很多。

在 0602 里它是延伸，正好对应那句三个传感器开会：ESPHome 节点本地判断是主方案，Node-RED 可以做上面那一层更复杂的决策。三个传感器读数通过 MQTT 进来，加一个 open-meteo 的 HTTP 节点拉未来 6 小时降雨概率，函数节点算出每区该浇几分钟，再按芒草 18%、朴树 25%、野花 22% 的阈值分三路发开阀指令，浇灌记录写进 InfluxDB。哪天想加一个条件比如连续三天高温就多浇两分钟，拖一个节点就行。注意 Node-RED 挂了不能让草地断水，ESP32 本地的兜底逻辑要留着。

open-meteo/open-meteo ★ 6.2k 无中文 延伸

免费开源的天气预报 API：整合全球十几家气象机构的模式数据，不用注册、不用密钥，一条 URL 拿到逐小时预报

→ 方案里那条未来 6 小时无雨才开阀的判断需要一个预报源，open-meteo 免费、无密钥、HomeAssistant 原生集成，是最省事的选择

Open-Meteo 是瑞士开发者 Patrick Zippenfenig 2022 年发起的开源天气 API，Swift 写的，6.2k 星，非商业用途免费。它解决的问题是：各国气象局的数值预报数据是公开的，但格式古怪、体积巨大；Open-Meteo 把它们统一下载、切片、缓存，包成一个干净的 HTTP 接口。

它的工作方式是：后台持续拉取 ECMWF、德国 DWD、美国 GFS、中国 CMA 等十几家机构的模式输出，转成自己的压缩格式；请求进来时按经纬度找最合适的高分辨率模式，插值出该点逐小时的温度、降水概率、风、辐射、土壤温湿度等上百个变量，返回 JSON。除了预报还有历史气象、空气质量和地理编码接口，整套服务可以自己用 Docker 部署。

生态上它有官方客户端库，HomeAssistant 内置了 Open-Meteo 天气集成，Node-RED、Grafana 都有现成节点。文档全英文，但接口简单。

在 0602 里它是延伸，但几乎是刚需：方案里 ESP32 开阀的三个条件之一是未来 6 小时无雨，这需要一个外部预报源。在 HomeAssistant 里加 Open-Meteo 集成，取杭州本地网格逐小时降水概率，做一个模板传感器：未来 6 小时最大降水概率大于 50% 就置为将要下雨，通过 MQTT 推给木杆里的 ESP32 当第二个条件。它还能给出蒸散量预报，可以试着用它修正每区的浇灌分钟数。免费额度每天一万次，每十分钟拉一次绰绰有余。

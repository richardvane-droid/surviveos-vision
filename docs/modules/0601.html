草地 · 模块 0601 · 稀树草原环境系统

谁懂啊！100㎡ 长条草地被我做成了一小片非洲稀树草原

一片不用割的草原，几棵歪脖子树，风一吹整片草浪往一个方向倒。

✅ 真实三阶段已完成 #自然生活#露营风#精神领地#疏林草原#低维护

📐 它在哪、有多大

整片草地在建筑东侧，5.3×18.9m 的南北长条、100㎡：北段 ≈7m 挨着邻居东墙是疏林带，中段 ≈7m 正对地堡和木屋东墙是草原带，南段 ≈5m 挨着庭院是野花点缀带；乔木沿东侧长边错开，靠建筑一侧留一条贯穿南北的视线通廊。

🎬 沉浸式想象

傍晚六点半，你端着一杯冰镇乌龙从木屋南门出来，穿过庭院往东一拐，拖鞋踩上的不是修得平平整整的草坪，而是齐小腿高的细叶芒和狼尾草，穗子已经泛金，被风一吹哗啦啦朝南边河那头倒。三棵朴树歪在草地北头，树影拉得老长，落在一块半埋的青石上，那是你专门留的“看草石”。你坐下，脚下草根处有极轻微的“嗒嗒”声，是地埋滴灌在工作，可你一根管子都看不见。今天上午你刚沿着长边走完一轮：手拔、打草机、修枝剪、吹叶机，四件家伙都是从过道那面工具墙上摘下来的，共用一块 WORX 电池，一个半小时收工。这条 19 米长的草地没有一条直线，但每一棵植物都是按图纸排的。

✅ 设想方案清单

  1. 沿长条分三段：北段 ≈35㎡ 疏林带（挨邻居东墙那头），中段 ≈40㎡ 草原带（细叶芒、狼尾草、蓝羊茅混播，正对地堡木屋东墙），南段 ≈25㎡ 点缀带（挨庭院）
  2. 疏林带 3 棵朴树沿东侧长边错开，间距 4m 以上，中段东缘再单放 1 棵乌桕，故意选歪脖子的苗，树下铺碎树皮护根
  3. 南段点缀带走“草原野花”路线：金光菊、松果菊、马鞭草三种，每平米 6 株，成活后自播扩张
  4. 所有滴灌管地埋 15cm，1.6mm 内嵌式滴头，出土口只在树根处露 3cm，表面盖蒲席草
  5. 中段靠建筑那侧留一块 60×80cm 半埋青石当“看草石”，坐下正好顺着长边看到北头的树，旁边压一块桧木牌写各分区植物名，动手主义
  6. 边界不用围栏，用 30cm 宽的碎石干河道沿庭院东边界分隔草地和庭院，雨天顺便当排水沟
  7. 草原带每年只贴地割一次，二月底整片放倒，草秆垫到疏林带做覆盖；平时的长度靠每周一次的养护巡场压住，秋冬减成两周一次
  8. 每周四步养护仪式：手拔 → 电动打草机 → 手动修枝剪 → 大风量吹叶机，四件都来自 0401 那面墙、共用一块 WORX 20V 电池，固定从北头起手、碎屑最后吹进干河道

Seeed-Studio/grove.py ★ 166 无中文

Seeed 给 Grove 模块写的 Python 库，面向树莓派这类单板机，一百多种传感器统一成四线接口，导入即读物理量

→ 0805 定下全屋传感器统一走 Seeed 的 Grove 接口，这是官方的 Python 读取库；三段草地在定植物表之前要先点测一个月，拿它凑采集脚本最省事。

grove.py 是 Seeed 给自家 Grove 模块写的 Python 库，面向树莓派这类嵌入式单板机。Grove 是 Seeed 用了十几年的四线标准接口，把一百多种传感器和执行器统一成同一个插头，接反了也烧不掉；0805 把它定成全屋传感器的基准形态，这个库就是在单板机那一侧读它们的官方实现。

用法是一行一个模块：导入对应的类，告诉它接在哪个口，读回来就是换算好的物理量，不用自己查寄存器、算分压。库里分 I2C、模拟、数字和 UART 四类驱动，土壤湿度、光照、温湿度、气压、超声波测距都有现成类，配一块 Grove Base Hat 插上就能跑，十几行脚本就是一套临时采集。

仓库 166 星，README 和示例都是英文，但每个模块在 Seeed Wiki 上都有中文页，接线图和量程一查就有。它更适合做原型和短期采集，长期挂在户外的常驻节点还是交给 XIAO 加 ESPHome，两边共用同一批 Grove 模块，换主控不用换传感器。

放进 0601 就是定植物表之前那一轮点测：一块单板机配 Grove Base Hat，把 Grove 土壤湿度、光照和温湿度模块沿疏林带、草原带、点缀带各埋一组，脚本每十分钟记一次写成 CSV，跑满一个月再决定哪段种芒草、哪段要垫高种蓝羊茅。测完模块拆下来，直接转给 0602 的常驻杆接着用。

danielbrendel/hortusfox-web ★ 1.7k 无中文

自托管的植物管理与追踪系统，按位置分组建植物档案，带任务、日历、库存、天气和二维码，Docker 一条命令跑起来

→ 把疏林带、草原带、野花带建成三个位置，每棵朴树、每片芒草建档，二月割草、补播野花的养护任务进日历按月提醒

HortusFox 是德国开发者 Daniel Brendel 做的开源植物管理系统，GitHub 上 1.7k 星，是自托管圈子里目前最活跃的植物档案工具。它解决的问题是：家里、院子里几十上百株植物，谁在哪、上次浇水施肥是什么时候、什么季节该做什么。

它是 PHP 加 MariaDB 的网页应用，官方 Docker 镜像一条 compose 命令就起来，多人协作。核心结构是位置和植物：先建位置，再把植物挂进去，每株有名字、学名、照片、光照需水等属性和一条完整的操作历史；任务系统给植物或位置挂待办，日历系统按日期排养护事项并发提醒；还有库存管理、天气接入、群聊、二维码标签、REST API 和外部植物识别。暂无中文包，但结构简单。

在 0601 里它是分区养护日历：建疏林带、草原带、野花带三个位置，三棵朴树和一棵乌桕各建一株，芒草、狼尾草、蓝羊茅按片建档，金光菊、松果菊、马鞭草记种植日期和自播情况；日历里写死几条年度任务，二月底整片贴地割草、割下的草秆垫到疏林带、梅雨前检查地埋滴灌出土口、秋天补播野花。桧木牌上的植物名和它里面的名字保持一致，手机扫二维码就能看这棵树的历史。要注意它没有 HomeAssistant 集成，提醒靠邮件或它自己的通知，可以用 REST API 让 HomeAssistant 每周拉一次到期任务推到手机。

openfarmcc/OpenFarm ★ 1.7k 无中文

曾经的开放种植知识库，收录大量植物的间距、需水、光照、土壤和伴生信息，2025 年 4 月已归档，代码和数据仍可下载

→ 网站已关但数据还在，选种时查芒草、松果菊、朴树这类植物的株距、需水量和耐旱性，按它的数字定每平米株数和滴头间距

OpenFarm 是 2014 年由 FarmBot 创始人 Rory Aronson 众筹发起的开放种植知识库，口号是你可以种任何东西，GitHub 上 1.7k 星。它想解决的问题是：植物怎么种的知识散落在各种书和论坛里，格式不统一也不开放，于是做了一个人人可编辑的种植指南数据库，像种植版的维基百科。项目在 2025 年 4 月归档，网站已关，但仓库是只读状态，代码和数据导出仍然能拿到。

它是 Ruby on Rails 加 MongoDB 的网页应用，核心数据是两层：作物条目记录每种植物的学名、株距、行距、播种深度、需水、光照、土壤酸碱和成熟天数；种植指南由用户按气候和方法写步骤，可以有多份。所有数据 CC 协议开放，有 JSON API，别人做的种植 App 很多都从它拉数据。README 只有英文，没有中文资料，但字段都是数字，看得懂。

在 0601 里它是选种和排布时的资料库：细叶芒、狼尾草、蓝羊茅、金光菊、松果菊、马鞭草、朴树、乌桕，每种查一遍株距和需水量，草原带混播的每平米株数、野花带每平米 6 株、朴树 4 米以上间距，都能对着它的数字校一遍，再决定地埋滴灌每米放几个滴头。用法是把仓库克隆下来跑一个本地实例，或者直接读数据导出文件。要注意它以北美和欧洲的作物为主，本地乡土种如朴树、乌桕可能没有条目，用同属植物的数据代替，再结合杭州本地苗圃的经验。

Ecohackerfarm/powerplant ★ 94 无中文

基于朴门永续原则的种植规划应用，内置植物伴生关系数据，给出哪些植物搭在一起互利、哪些相克，并排种植时间表

→ 小众但没有更好的替代：草原带混播和野花带选种时查伴生关系，避免把互相压制的种混在一起，是朴门伴生规划的少数现成工具

powerplant 是德国 Ecohackerfarm 朴门农场做的开源种植规划工具，GitHub 上 94 星，社区小，但它是少数把朴门永续里的植物伴生关系做成可查可算的软件，而不是一张纸质对照表。它解决的问题是：一块地里种多种植物，哪些搭在一起互利、哪些互相压制、哪些吸引害虫的天敌，这些知识分散在书里，规划时很难一次看全。

它是 Node.js 后端加 React 前端的网页应用，核心是一份植物数据库和一张伴生关系矩阵，数据来自朴门社区整理的开放资料。用法是先建一块地，往里加想种的植物，它会给每对植物打分，绿的互利、红的相克，并按你的气候区排出播种和移栽的时间表；也能反过来问它，已经种了 A，还能配哪些 B。数据可导出，没有 HomeAssistant 接口，也没有中文资料，界面是英文但操作只有拖拽和勾选。

在 0601 里它用在选种阶段：草原带的细叶芒、狼尾草、蓝羊茅三种混播，野花带的金光菊、松果菊、马鞭草，加上疏林带的朴树和乌桕，全部录进去看一遍关系矩阵，确认没有明显相克的组合，再决定混播比例；朴树树下的碎树皮护根圈里以后想加点地被，也先在它里面配一下。要注意它的数据库以蔬菜和果树为主，观赏草和乡土乔木条目少，查不到就按同科同属替代，把它当一个提醒工具而不是最终裁判。

qgis/QGIS ★ 14.3k 有中文文档站 延伸

全球最流行的开源桌面 GIS：加载卫星图和无人机正射图，画地块、量面积、做坡度与日照分析，上千插件

→ 100 平米的草地分三段、每棵树有位置、滴灌管地埋看不见，需要一张真正的地图而不是一张草图，QGIS 就是这张图的底稿

QGIS 是 2002 年起步、由 QGIS.org 基金会维护的开源桌面地理信息系统，C++ 和 Python 写的，14.3k 星，是商业软件 ArcGIS 之外最常用的选择，市政、林业、考古和农业项目都在用它。它解决的问题是：任何带坐标的东西，地块、树、管线、传感器，都能画在同一张图上，量长度和面积，叠上卫星图、地形和年份做分析。

它的工作方式是图层：底图可以是在线瓦片（天地图、OpenStreetMap、卫星影像）或本地的无人机正射图；矢量图层用来画点线面，每个要素带一张属性表；栅格图层是高程或影像，可以算坡度、坡向、日照和视域。处理工具箱里有几百个算法，还能用 Python 写脚本批量跑。输出是打印布局里排好的地图，或者导出 GeoPackage、KML。

生态非常大：插件仓库上千个，官方培训手册和用户指南有简体中文翻译，界面也有中文，国内高校和公众号教程极多。项目每四个月发一个版本，长期支持版稳定。

对 0601 来说它是延伸：草地 5.3 乘 18.9 米、三段分区、三棵朴树和一棵乌桕错开、地埋滴灌管和出土口，这些东西画在纸上迟早对不上。用手机 GPS 或卷尺量几个角点，在 QGIS 里建一个本地坐标的工程，一层画分区、一层画树、一层画滴灌管和 0602 的三路阀门，属性表里记品种和种植日期。年底把 0604 全景机拍的照片配准进去，就能看到草浪的实际范围和图纸差多少；再叠一层 0603 雨水罐的溢流走向，碎石干河道该挖多深也有了依据。

OpenDroneMap/ODM ★ 6.5k 有中文文档站 延伸

开源的无人机航拍处理工具链：一堆带 GPS 的照片进去，正射影像、点云、数字高程模型和三维网格出来

→ 让无人机绕草地飞五分钟，ODM 就能拼出一张厘米级的俯视图和地形高程，草地的排水坡向和树冠大小一目了然

OpenDroneMap 是 2014 年发起的开源摄影测量项目，ODM 是它的命令行核心，Python 写的，6.5k 星。它解决的问题是：消费级无人机拍的几百张照片怎么变成一张有坐标的正射影像和一份地形数据，而不用花几万块买 Pix4D 或 Metashape。

它的流程是典型的运动恢复结构：先从每张照片提取特征点并两两匹配，用 GPS 和相机参数做稀疏重建得到相机位置，再做稠密点云、网格和纹理，最后把纹理正射投影生成正射影像（GeoTIFF）和数字表面模型、数字高程模型。全部步骤跑在 Docker 里，一条命令带上照片目录就开始算，可以选质量档、是否生成三维模型、是否用地面控制点提高精度。

生态上它有图形界面版 WebODM，可以在浏览器里上传照片、看进度、量面积和体积、做剖面；NodeODM 能把计算分到多台机器；有官方 Docker 镜像，文档站有中文翻译，国内测绘和农业圈教程不少。

在 0601 里它是延伸：草地不大，但一张正射图能回答很多草图回答不了的问题。用无人机在 30 米高绕草地和庭院飞一圈，拍 80 到 150 张带 GPS 的照片，在 0802 服务器上跑一次 ODM，就得到整块地的厘米级俯视图和高程模型。高程模型能看出草地往哪边低、碎石干河道该开在哪、乌桕树冠到底遮了多少草原带；正射图直接拖进 QGIS 当底图，三段分区和滴灌管画在真实的地面上。每年秋天穗子泛金时飞一次，几年后就是一部草地的地图史。
